# eagler-touhou 实际中继接入核对

2026-10-04。依据新提供的 eagler-touhou-main/eagler-touhou-main 源码；仅阅读和文档整理，没有启动服务器、浏览器、游戏或测试，没有修改运行代码。

## 结论与当前验收边界

可以向该主项目靠齐。应复用它的部署、中继、房间和运行参数入口，保留 TH04 的 NP21 状态快照、回滚、输入和游戏规则。无需为了这条路线购买 TURN 或单独购买服务器。

用户已实测临时 WebSocket 中继可以跨网进入游戏；公网连通可行性已得到有限验证。实测约 460–640 ms 应用层 RTT、2–4 同步步/秒，不能称为流畅验收，也不能据此确认正式服务的表现。应用层 RTT 包括浏览器调度。手机执行均值约 24–28 ms 也是独立性能约束。

## 实际接口差异

| 项目 | 主项目源码 | TH04 当前实现／处理要求 |
| --- | --- | --- |
| 游戏连接 | room/run/player/players 查询参数；signal=1 为信令连接 | 当前 /relay 使用 room/token；需要会话适配，不能直接换 URL |
| 定向封包 | E7 + target + payload；服务端剥掉前两字节，原样转发 payload | 当前接收要求 E8 + 服务端确认的 source + JSON，不兼容 |
| E8 | 已用于旁观者发布数据 | 不可把 TH04 E8 扩展直接套在现有服务上 |
| 开局路由 | route 消息只有 type/mode；默认约 4500 ms RTC 等待后可选 relay，全员 relay 到齐才释放 | 当前要求 generation 字段；适配时通过 room/run 隔离局次，保留 TH04 自身 generation 校验 |
| 成员编号 | 大厅按座位编号，P1 管设置和开始 | TH04 host/guest 身份与座位独立，房主可以 P2/P3；需明确映射及管理员政策 |
| 离线 | 游戏连接关闭清理；成员释放可关闭传输，未发现 TH04 peer-left 消息 | 适配大厅成员事件、关闭和心跳，继续走 TH04 确定性离线屏障 |
| 游戏内容 | 中继可以转发任意二进制 payload；特定输入识别用于故障注入 | UTF-8 JSON 可以作为二进制 payload，不必改成 TH06 的游戏输入格式 |
| 产品入口 | src/contracts/product-catalog.mts 未发现 TH04 注册项 | 正式大厅需要补产品及运行适配，不是复制一个 html 即完成 |

服务端游戏连接路径检查房间/局次/编号格式、人数、重复槽位和已释放成员，但没有当前 TH04 room token 的等价验证。不能把客户端自填 source 或 member 编号称为服务端认证身份。

## 建议的最小路线

1. 先独立适配正式中继传输，不动回滚，也暂不搬整个大厅。保留现有 LAN 和临时 public-ws 模式，新增明确独立的宿主接入模式。
2. 发送者来源必须有明确方案。推荐给正式中继增加仅对 TH04、且显式协商启用的来源封装：服务端从连接 player 生成来源，使用独立协议标识，不占已有 E8 旁观者分支；原 TH06/07/08 连接行为不变。这需要交付一个小的服务端补丁供主项目维护者接入。若要求服务端零修改，可以自定义 payload 内的来源字段，但这只是客户端声明，不能保留原身份保证；三人模式尤其不能仅靠“唯一另一端”推断。不要无声降低保证。
3. 适配 room/run、来源与目标编号、route 开局屏障和关闭事件。处理 route 到达不同端的短暂时间差，开局释放前有界缓存合法包；不允许缓存无限增长或跨局复用。TH04 hello/ready/run 和版本检查仍执行。
4. 再添加宿主运行入口，把 URL、人数、种子、难度、座位、管理员身份映射给 TH04。主项目现有 P1 管理政策与 TH04 独立房主不同，单纯重编号不能消除该差异；接入时需为 TH04 保留独立 owner 信息及对应大厅权限。普通 LAN 无需改权限。
5. 最后使用主项目现有服务部署完成异网验收；服务器地址、部署权限和上线操作由主项目维护者提供。TH04 侧负责可运行的适配器、服务端补丁和接口说明，不能把协议不兼容全部留给对接人。

不在此轮引入观战、中途重连、主机迁移、全套账号服务，也不复制 TH06 对象回滚到 NP21。正式 RTC 优先/relay 回退可以在强制 relay 验收后增加，避免同时更换房间、路由和同步算法。

## 延迟判断

netplay-relay.mjs 默认 delay/jitter/drop 均为 0，正常转发直接 target.send；没有发现特殊机制可以消除网络传播延迟。Node ws 异步转发与当前 Python 共享锁内发送不同，但没有压测证据，不能将 500 ms 归因于 Python。换到距离玩家更近的正式服务可能改善路径，需要实测确认。

TH06 也使用有限预测窗口，且部分菜单/切换状态必须等真实输入。TH04 应先补“禁止预测／窗口耗尽／补算中／等待真实输入”等等待原因，再判断 4 步/秒的实际瓶颈。不能仅增加到数十帧完整机器快照来补高延迟。

## 分阶段验收

| 阶段 | 交付 | 人工验收标准 |
| --- | --- | --- |
| A 正式中继协议 | 独立传输适配及必要的 TH04 专用服务端封装 | 两人及三人正确收到定向包；来源由服务端生成；route 前不提前开局；旧局包不进入新局；原产品封包路径不受影响 |
| B 游戏接通 | 沿用当前大厅建立 TH04 会话并连接同版正式中继 | 异网实际战斗 10–15 分钟，状态摘要持续推进且一致；房主 P2/P3 可用；客机离线后其余玩家按现有规则继续；房主离线结束 |
| C 宿主大厅 | 产品注册、运行参数与成员生命周期适配 | 在主项目内建房、准备、开局、退出回大厅；双人/三人座位和房主权限正确；不再依赖个人电脑的 Python 房间服务 |
| D 性能与回归 | 等待原因指标、正式部署实测记录 | 记录场景、RTT、模拟耗时、重算、等待和同步步速；以能独立达到目标步速的设备检验正常战斗是否接近 60 步/秒；慢手机单独记录上限；原 LAN 与同屏人工回归通过 |

可由代码完成：连接适配、来源封装、会话映射、诊断、产品入口和部署配置模板。需要人工／维护者：提供正式 WSS 地址与部署权限、批准并部署主项目补丁、在不同网络和真实设备试玩。没有要求用户先开通 TURN 或购买服务器。
