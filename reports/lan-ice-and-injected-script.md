## 用户提供的证据

- 两台设备使用同一路由器/同一 Wi-Fi，出错浏览器安装过用户脚本类扩展。
- 双方资源加载完成 7/7，协商 stable，房主已收到 answer，候选本机/收到/提交各 1。
- 数据通道仍 connecting，ICE disconnected，曾报告 connectionState failed；本局由 30 秒建连超时停止。

项目 web 源码没有引用上述加载器。站外脚本注入与用户安装的脚本扩展相符，但没有直接检查用户扩展及其脚本，不能指定某个扩展为已确认根因，也不能把报错与 ICE 失败混为同一原因。页面异常目前仅记录；真正结束游戏的是建连超时。没有生成 `window.Player` 来掩盖错误，也没有抑制异常事件。

资源就绪只证明磁盘/引擎加载完成；stable 只说明这一端 SDP 协商完成，不能证明网络路径已通。候选各 1 不足以判断是否配置 STUN、候选类型、网络隔离或防火墙。相同 SSID 也不保证设备之间可以直接互访。

## 本次代码改动

- 显示实际交给 PeerConnection 的配置摘要：STUN/TURN 地址数量及 all/relay 策略，不显示地址和凭据。
- 显示本机与收到的 trickle 候选的 host/srflx/relay/prflx 类型、收集状态。只统计信令事件中的候选，不声称枚举了 SDP/ICE agent 内部的全部候选。
- 记录 `icecandidateerror` 的服务类型和错误码，最多保留 5 种，不记录可能包含网络地址的 errorText、URL、SDP 或 TURN 凭据。没有错误事件不等于 ICE 服务一定可达；701 也不是整条连接失败的充分证据。
- 超时停止之前刷新加载诊断快照，避免冻结在前一秒的显示。
- 对来源或堆栈包含非当前 origin 的 HTTP(S) URL 的页面异常增加站外脚本提示。保留原始错误，提示做扩展对照，不自动终止游戏。这只是来源线索，不是判定扩展恶意或 ICE 根因。
- 回滚、可靠有序数据通道、默认空 ICE 配置、信令协议与超时时间不变。

## 用户操作：先做一个变量的对照

1. 双方刷新到同一新版。使用原局域网入口，先不增加 Tunnel、TURN 或更换网络。
2. 在出错浏览器暂停相关用户脚本/扩展，然后刷新页面，重新建房。暂停不会撤销已经注入当前页面的脚本，所以必须刷新。
3. 也可用 Chrome 访客窗口做干净环境对照；普通无痕窗口不是绝对保证，因为扩展可能被允许在无痕中运行。
4. 如果之前手动设置过连接配置，刷新后会丢失；为了比较，应在两轮保持相同配置。同一局域网默认空 STUN/TURN 是原有行为，不等于配置错误。比较两端显示的“本机实际连接配置”。
5. 先确认站外脚本异常是否消失，再观察数据通道是否打开。偶发问题建议重新建房试 3 次，不以一次成功证明修复。
6. 若干净环境成功，可逐个恢复相关脚本，在刷新重建后复现，才能定位具体脚本；无需修改第三方脚本里的 Player 或先删除全部扩展。

## 结果如何判断

| 结果 | 下一步 |
|---|---|
| 异常消失且多次联机成功 | 支持浏览器环境相关假设；逐个恢复脚本定位。未完成对照前不确认哪个脚本是根因 |
| 异常消失但 ICE 仍超时 | 单独排查局域网；保存双方完整新诊断、浏览器/设备型号、使用的是局域网地址还是 Tunnel |
| 访客环境仍有同一站外脚本异常 | 继续检查实际干净环境、其他注入来源；不能认定常规用户脚本扩展已排除所有可能来源 |
| 同一 Wi-Fi 仅 host 候选且不通 | host-only 在局域网可以正常；检查访客网络/AP 客户端隔离、VPN/虚拟网卡及特定应用防火墙规则，不直接关闭整机防火墙 |

## 手机与电脑的后续隔离检测

用户后续明确是手机与电脑，仍只有 host 候选各 1、无 STUN/TURN、收集 complete；站外脚本错误也仍存在。尚未得到手机系统/浏览器和电脑访客窗口对照结果。

源码确认：runtime.boot 在 NP21.create、挂盘和音频采样率检查后报告 7/7。room.maybeRun 要求所有通道 open 且 hello/ready、版本一致、获得 run 才调用 runtime.start；模拟器随后在同步帧中 step。没有 DOS 画面与等待网络门槛相符，不能将它直接判为模拟器初始化失败。

新增 `connection-check.html`（从 lan.html 的“连接排查”打开），双方必须使用该页面的新检测房间。无需复制控制台命令：电脑建房、手机输入六位码，检测页自动选座/准备，然后使用现有房间 API 交换 SDP/ICE，以可靠有序 DataChannel 每秒互发 ping/pong。页面仅加载检测 JS 和 connection.js，不加载 NP2、游戏磁盘、回滚模块或音频。固定空 ICE 配置，不读取宿主注入的连接配置，专门对照当前局域网失败场景。

检测保留本地/远端候选类型、ICE 与通道状态、收发计数、RTT 和浏览器标识；不展示 IP/SDP/令牌/凭据。30 秒未收到有效回包判失败，首次收到回包后继续观察；超过 10 秒无后续回包则报告中断。房间 HTTP 请求失败独立报告，不能当成 ICE 失败。页内异常独立记录。退出/重试发送 leave；测试房间必须与游戏房间分开，不操作已有游戏房间。此页没有自定义新的游戏掉线语义。

人工步骤：

1. 用原局域网 URL，电脑优先使用 Chrome 访客窗口，手机使用独立浏览器而非聊天应用内嵌网页。双方打开检测页并保持前台。
2. 建房/加入，确认两端都显示“双向数据收发成功”，观察约 30 秒回包持续增长。
3. 若成功，再用相同浏览器/网络测试游戏页面：仍失败则重点检查游戏页面初始化负载、页面注入和生命周期差异，不能仅凭轻量探测成功宣称游戏兼容。
4. 若检测页也 ICE 失败，说明不依赖 NP2 即能复现，优先查手机/浏览器、mDNS 候选解析、VPN、网络客户端隔离和应用防火墙；仍不能仅凭 host 类型指定唯一根因。
5. 任何一种失败，提供两端完整检测结果。检测页成功不保证游戏吞吐、实时性、确定性或公网连接。

本次检测页只做静态语法检查与差异检查；未由 AI 启动或运行。未修改构建依赖内的游戏运行文件，因此无需为独立检测页重建游戏清单。

### 后续线索：手机 P1 与 P2 的差异

用户报告手机换浏览器仍一样，但此前成功过；最新发现手机作为 P2 可正常使用，作为 P1 失败。随后用户明确：无论谁创建房间，手机选 P1 都不能运行、选 P2 正常。已排除“用户只是把房主称为 P1”的解释，不要再让用户重复该澄清，也不要继续将它归为手机整体不兼容。

静态追踪：room.js 的 PeerConnection、offer 发起与 answer 校验只依赖 `host/guest/guest2` 身份次序，不读取 slots；slots 影响 RollbackQueue、本机输入归属及暂停权限。runtime.configure 的 host/local 都接受任意合法座位，7/7 之前不按 localSlot 区分加载。两人局创建房间者为 offer 发起端，即使他坐 P2。尚未发现“手机不能坐 P1”的显式限制。

已继续追踪：RollbackQueue 构造函数显式接受整数 0；server seat/ready 使用 is None 检查，客户端使用 ===null，没有发现 P1=0 被直接误当作未选座。runtime 的 localSlot 只记录本机座位，初始化不依赖该值；本机 P1/P2 均运行完整的同一磁盘。P1 原生输入与 P2 mailbox 输入的区别在模拟推进后才发生，不能直接解释已给出的 DataChannel 尚未 open 阶段故障。这些静态证据不足以否定用户复现，也尚未定位修复点。

因此独立检测页新增手动 P1/P2 选择，保留相同房间座位状态，但不加载模拟器。下一轮固定电脑建房：先电脑 P2、手机 P1，再电脑 P1、手机 P2，每次新建房。若检测也随座位失败，继续追踪房间/API/页面环境；若两组检测都成功而正式游戏只有手机 P1 失败，再定位游戏页面启动/帧队列路径与时序。检测日志同时显示身份、座位、浏览器、连接状态和收发结果。不通过交换或强制限制手机座位冒充修复。
